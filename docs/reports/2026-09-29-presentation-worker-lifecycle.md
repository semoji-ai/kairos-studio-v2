# PPT 워커가 앱 종료 후에도 영원히 남는 문제 (리포트)

- 작성일: 2026-09-29 (Windows 11, 설치본 `%LOCALAPPDATA%\Kairos Studio`)
- 상태: **리포트만** — 코드 수정은 이 PR에 포함하지 않는다.

## 설계 의도 (유지해야 할 것)

`spawn_presentation_worker` (`src-tauri/src/lib.rs`)는 PPT 워커를 API 사이드카와
분리해 띄운다. 앱 창이 실수로 닫혀도 진행 중인 PPT 작업이 날아가지 않게 하려는
의도이고, 이 의도는 맞다. 문제는 **작업이 끝난 뒤에도, 큐가 비어 있어도 워커가
끝나지 않는다**는 점이다.

## 관찰한 증상

1. 앱을 정상 종료해도 `python-embed\python.exe -m core.presentation_worker`가 남는다.
   같은 날 두 번 연속 재현 (PID 28768 — 15:09 기동, PID 33252 — 15:40 기동).
   부모 `app.exe`는 이미 종료된 상태였다.
2. **업데이트 설치 후에도 옛 워커가 계속 돈다.** NSIS 설치는 성공(exit 0)하지만,
   이미 메모리에 올라간 옛 코드 워커가 싱글턴 락을 쥐고 있어 새 앱이 띄운 워커는
   `BlockingIOError`로 바로 빠진다. 결과적으로 업데이트 뒤에도 PPT 작업은 옛 코드로
   처리된다.
3. **같은 작업이 두 달째 처음부터 다시 돈다.** 작업 `d86fe7bdf49f`
   (「인간의 세 가지 근원적인 갈증」, 2026-07-24 생성)는 `status.json` 로그에
   "Markdown 변환 완료"가 5회 찍혀 있고, 매번 전략·이미지 계획 단계부터 다시
   시작한다. 2026-09-29 15:54에도 새 워커(PID 20228)가 이 작업을 다시 잡았다.
   같은 제목의 다른 작업 `c85d8351e81a`는 이미 `completed`다.
   워커가 강제 종료될 때마다(작업 관리자, 설치, 재부팅) 복구 로직이 `running`
   작업을 `queued`로 되돌리고, 앱을 켤 때마다 다시 처음부터 codex를 돌린다.
   구독 사용량을 계속 소모한다.

## 원인 (코드 기준)

| 위치 | 내용 |
|---|---|
| `src-tauri/src/lib.rs` `spawn_presentation_worker` | 워커 PID를 어디에도 보관하지 않는다 (`SidecarState` 제외가 의도). 앱 종료 경로(`reap_sidecar`)는 사이드카만 죽인다. |
| `core/presentation_worker.py` `run_worker` | `while not stop:` 루프에 **종료 조건이 신호뿐**이다. 큐가 비어도 1초마다 폴링하며 영원히 돈다. |
| 같은 파일, 신호 처리 | Windows에서는 `SIGTERM`을 외부에서 보낼 방법이 사실상 없다 (`taskkill /F`는 즉시 강제 종료라 `request_stop`이 불리지 않음). 즉 Windows에서는 우아한 종료 경로가 없다. |
| 같은 파일, 복구 | 재시작 시 `running` → `queued`로 되돌리는데 **재시도 횟수 제한이 없고**, 중간 산출물에서 이어 하지 않고 처음부터 다시 한다. |
| 설치 프로그램 (NSIS) | 설치 전에 워커를 멈추는 단계가 없다. |

## 개선 방향 (제안 — 구현은 별도 PR)

1. **유휴 종료**: 큐가 비어 있고 앱(사이드카)이 살아 있지 않은 상태가 N분(예: 10분)
   지속되면 워커가 스스로 종료. 앱 생존 여부는 사이드카가 갱신하는 하트비트 파일이나
   사이드카 포트 `/health`로 판단. → "실수로 꺼져도 작업은 끝까지"와 "영원히 남지
   않음"을 동시에 만족.
2. **버전 불일치 시 교대**: 새 앱이 뜰 때 `worker.json`에 워커의 번들 버전(또는 빌드
   해시)을 기록·비교해, 옛 워커면 현재 작업을 마친 뒤 종료하도록 요청 (정지 요청 파일
   `worker.stop` 같은 파일 기반 신호 — Windows에서도 동작).
3. **재시도 상한**: 복구될 때마다 `attempts`를 올리고, 상한(예: 3회)을 넘으면 `failed`
   로 표시하고 사용자에게 알림. 가능하면 이미 만든 `design_spec.md`/`image_prompts.json`
   이 있으면 그 단계부터 이어서.
4. **설치 전 정지**: NSIS preinstall 훅에서 정지 요청 파일을 쓰고 잠시 대기 → 남으면
   종료. (현재는 설치 중 파일 잠김 위험도 있음.)
